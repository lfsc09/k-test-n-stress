## Critical

Issues that represent correctness bugs, security vulnerabilities, or data-loss risks. Must be fixed before any new feature work.

### C1 — Duplicate CSV Header Row in Concurrent Path

**Location**: `cmd/mock.go` — `streamOutput` (lines ~1364–1388 outer loop, ~1322–1343 `writeItem` closure)  
**Description**: On the first item of the first batch, the outer batch loop (line 1364) writes the CSV header to both `stdoutCsvWriter` and `csvFileWriter`, then calls `writeItem(item, sep)` with `firstItem` still `true`. Inside `writeItem`, the guard `if firstItem && csvFileWriter != nil` (line 1330) fires again, writing the header row a second time to the CSV file. Every CSV file produced by the concurrent path (`--generate >= 10000`) therefore contains a duplicate header row, making the file non-conformant and breaking any downstream parser. The sequential path (`routeOutput` → `marshalAsCSV`) is unaffected.  
**Suggestion**: Remove the duplicate header logic inside `writeItem`. The outer batch loop already handles header initialisation; `writeItem` should only write data rows. Delete lines 1323–1333 in `writeItem` (the block that derives `csvHeaders` and the `if firstItem && csvFileWriter != nil` sub-block).

### C2 — Index-Out-of-Range Panic on Parameterised Functions Called Without Arguments

**Location**: `mocker/mocker.go` — `Generate` (lines ~198, ~286, ~292, ~298, ~303, ~311)  
**Description**: Six parameterised mock functions unconditionally access `functionParams[0]` without a bounds check:
- `Boolean.booleanWithChance` (line 198)
- `Lorem.paragraph` (line 286)
- `Lorem.paragraphs` (line 292)
- `Lorem.sentence` (line 298)
- `Lorem.sentences` (line 303)
- `Lorem.words` (line 311)

`extractMockMethod("Boolean.booleanWithChance")` (no colon) returns `params = []string{}`. Calling `Generate("Boolean.booleanWithChance", []string{})` panics at runtime with index out of range. The entire generation run crashes with no error message visible to the user (Cobra swallows the panic unless `-recover` is set).  
**Suggestion**: Guard each case with `if len(functionParams) == 0 { /* use default */ }` before accessing `functionParams[0]`. `Regex.regex` already does this correctly (line 392) — use that pattern.

### C3 — `sanitizeJsonMap` Does Not Recurse Into Arrays

**Location**: `cmd/mock.go` — `sanitizeJsonMap` (lines ~840–860)  
**Description**: `sanitizeJsonMap` only recurses into `map[string]any` values. It does not walk `[]any` slices. A template like `{"outer[2]": {"inner[3]": "{{ Person.name }}"}}` produces — after `processJsonMap` — an array under the key `outer[2]`, where each element is a map still carrying the key `inner[3]`. When `sanitizeJsonMap` runs, it sanitises `outer[2]` → `outer` but skips the array's contents. The final JSON/CSV output contains literal `inner[3]` as a map key, corrupting the output schema for any nested `[n]` template.  
**Suggestion**: Add an `[]any` branch in `sanitizeJsonMap` that iterates the slice and recurses into any `map[string]any` elements, mirroring the pattern already used in `processJsonMap`.

## Must Act

Real problems that degrade reliability, maintainability, or correctness but are not immediately catastrophic. Should be addressed in the next planning cycle.

### M1 — `regexp.MustCompile` Called Inside Hot Functions

**Location**: `cmd/mock.go` — `interpretString` (line 725), `extractDigitInBrackets` (line 926)  
**Description**: Both functions compile a regular expression on every call. `interpretString` is called once per JSON key per generated object; `extractDigitInBrackets` is called twice per key (once for strings, once for maps). At `--generate 100000`, with a 5-key template, this compiles the same regexp 1–2 million times per run. `regexp.MustCompile` is not cheap.  
**Suggestion**: Hoist both patterns to package-level `var` declarations alongside the existing `objKeyNumberRegex`. The `interpretString` pattern `^\s*{{(.*)}}\s*$` and the bracket-check pattern `[\[\]]` are both constant and safe to pre-compile.

### M2 — `http.Client` Has No Timeout in `request` Command

**Location**: `cmd/request.go` — `NewRequestCmd` `RunE` (line 117)  
**Description**: `client := &http.Client{}` uses Go's default, which has no request timeout. A hung or slow server will block the process indefinitely. There is no `--timeout` flag and no context-based cancellation passed to the request.  
**Suggestion**: Add a configurable `--timeout` flag (default 30s) and use `http.NewRequestWithContext(ctx, ...)` together with a `context.WithTimeout`-derived context, or at minimum set `client.Timeout`.

---

### M3 — `response-accessor` Flag Defined, Read, but Never Implemented

**Location**: `cmd/request.go` — `NewRequestCmd` (line 158, line 29)  
**Description**: The `--response-accessor` flag is registered and its read is commented out (`//responseAccessor := cmd.Flags().GetString("response-accessor")`). The flag appears in `--help` output, inviting users to use a feature that silently does nothing.  
**Suggestion**: Either implement the feature or remove the flag definition and its commented-out read line until it is ready.

### M4 — `Number.number` Silently Truncates Float `min`/`max` to `int`

**Location**: `mocker/mocker.go` — `Generate`, `"Number.number"` case (line 333)  
**Description**: `m.jaswdrFaker.Float64(decimals, int(min), int(max))` truncates `min` and `max` from `float64` to `int` before passing them to the library. A user specifying `{{ Number.number:{2}:{1.5}:{9.9} }}` silently gets `min=1, max=9` — different bounds than intended, with no error or warning.  
**Suggestion**: Either document that bounds are always integer-truncated, or switch to generating the float directly via `m.rng` using `min + m.rng.Float64()*(max-min)` rounded to `decimals`, eliminating the truncation.

---

### M5 — Unbounded `--generate` Allows Runaway Memory Allocation

**Location**: `cmd/mock.go` — `NewMockCmd` `RunE` (line 474)  
**Description**: `--generate` is validated only to be `> 0`. A user can pass `--generate 1000000000`, which causes the sequential path to pre-allocate a `[]map[string]any` of one billion elements, exhausting system memory. The concurrent path is safer (streaming), but the sequential path (`generate < 10000`) has no cap.  
**Suggestion**: Add a configurable or hard maximum (e.g., 10 million) with a clear error message, or ensure the sequential path uses streaming instead of a pre-allocated slice.

---

### M6 — `Boolean.booleanWithChance` Silently Falls Back on Parse Error Instead of Reporting It

**Location**: `mocker/mocker.go` — `Generate`, `"Boolean.booleanWithChance"` case (line 198–202)  
**Description**: If the `chance` parameter is not an integer (e.g., `{abc}`), the function silently ignores the error and generates a plain random boolean — making a misconfigured template indistinguishable from a correctly configured one. The user gets no feedback that their parameter was ignored.  
**Suggestion**: Return `fmt.Errorf("Boolean.booleanWithChance: invalid chance parameter '%s': %w", functionParams[0], err)` instead of silently falling back. The same pattern applies to `Lorem.*` and `Number.number` parse errors.

## Good to Know

Code quality observations, missed opportunities, minor inconsistencies.

### G1 — `request` Command Short/Long Description Is a Copy-Paste from `mock`

**Location**: `cmd/request.go` — `NewRequestCmd` (line 19–20)  
**Description**: `Short: "Generate mock data based from an object string or from template files"` is the `mock` command description. The `Long` field is empty. Any `--help` output for `request` is misleading.  
**Suggestion**: Update `Short` to describe the `request` command's actual purpose (e.g., "Make an HTTP request with optional mock data in the URL, headers, or body") and flesh out `Long` with examples.

### G2 — `Mocker` Interface Is Defined But Never Used

**Location**: `mocker/mocker.go` — `Mocker` (lines 18–21)  
**Description**: The `Mocker` interface declares `List` and `Generate` but no code in the project uses `Mocker` as a type — all call sites reference `*Mock` concretely. The interface provides no benefit today (no mocking in tests, no alternative implementation).  
**Suggestion**: Either use `Mocker` in function signatures where the concrete type is not required (e.g., `processJsonMap`) to enable future testing without a real faker, or remove it to reduce maintenance noise. This is low priority but worth addressing when tests are written for `processJsonMap`.

---

### G3 — Duplicate Test Runner Name `TestMockCmdTestSuite` Across Packages

**Location**: `cmd/mock_test.go` (line 17) and `cmd/mock_e2e_test.go` (line 22)  
**Description**: Both files define a top-level `func TestMockCmdTestSuite` — one in `package cmd`, one in `package cmd_test`. Go compiles these into the same test binary; both execute, running different suites. This causes confusing output in `go test -v` (two entries with the same name running different things) and can mislead CI diff tooling.  
**Suggestion**: Rename one of them. Suggested names: `TestMockCmdUnitSuite` (for `mock_test.go`) and `TestMockCmdE2ESuite` (for `mock_e2e_test.go`).

### G4 — `goregen` Dependency Is Unmaintained and Brings in `gxui`

**Location**: `go.mod` (lines 11, 15)  
**Description**: `github.com/zach-klippenstein/goregen v0.0.0-20160303162051` has not been updated since 2016. It pulls in `github.com/google/gxui`, an abandoned GUI framework. The library works for the current use case but has no active maintenance, no security fixes, and is a heavier transitive dependency than necessary.  
**Suggestion**: Evaluate replacement options (e.g., `github.com/lucasjones/reggen` or generating via `text/template` + `math/rand`). Not urgent, but track as a future dependency health item.

### G5 — `go.mod` Specifies Non-Existent Go Version `1.26.1`

**Location**: `go.mod` (line 3)  
**Description**: `go 1.26.1` does not exist as of April 2026 (the latest stable release is 1.24.x). This was likely set speculatively. While `go` toolchain version in `go.mod` is a minimum declaration and tools will still work, it may cause surprises with `go mod tidy` or CI toolchain pinning.  
**Suggestion**: Update to the actual Go version in use (`go 1.24` or whatever `go version` reports).

---

### G6 — No Integration Tests for Concurrent Output Path

**Location**: `cmd/mock_e2e_test.go`  
**Description**: All E2E tests use low `--generate` values (1–5), which always route through the sequential `routeOutput` path. The concurrent `streamOutput` path (`--generate >= 10000`) has no test coverage. The double-header bug (C1) was not caught because of this gap.  
**Suggestion**: Add at least one E2E test with `--generate 10001` (or set `concurrencyThreshold` to a test-injectable value) that verifies: correct item count in output, no duplicate CSV header row, and correct JSON array structure.

---

### G7 — `processStr` Errors Are Silently Embedded in Output

**Location**: `cmd/mock.go` — `processStr` (lines 901–909)  
**Description**: When `extractMockMethod` or `mocker.Generate` returns an error during `--parse-str` processing, the error string is injected inline into the output as `[error message]` instead of returning an error to the caller. The command exits with code 0 and the user receives malformed output with no stderr warning.  
**Suggestion**: Accumulate errors and either return the first error to `RunE` or at minimum `fmt.Fprintf(os.Stderr, ...)` a warning before substituting the error text.

---

### G8 — `calculateChecksum` Is Not Bounds-Safe

**Location**: `mocker/helpers.go` — `calculateChecksum` (lines 10–20)  
**Description**: The function iterates `for i := range digits` and indexes `multipliers[i]` without verifying that `len(multipliers) >= len(digits)`. If called with mismatched slice lengths, it panics. Both call sites (CPF and CNPJ) happen to be correct today, but the function has no guard.  
**Suggestion**: Add `if len(digits) != len(multipliers) { panic(...) }` (acceptable for a private function with invariant-based callers) or return an error. The existing unit tests do not test mismatched lengths.

Test coverage for the concurrent output path is the widest gap — it directly caused C1 to go undetected, and closing it should be the first priority alongside the bug fixes.
